# 4. The KR260 system and results

## The board
The AMD KR260 carries a K26 module: a Zynq UltraScale+ chip with
- an ARM processor side (**PS**) with 4 GB DDR memory
- an FPGA fabric side (**PL**)

Our two RISC-V cores live in the PL and use the PS only for its DDR memory and for loading programs. The ARM cores run no software.

## What is on the FPGA
```
 PL (FPGA)                                                    PS (ARM side)
 +-------------------------------------------------------+    +--------------+
 | core 0 --cut--+                                       |    |              |
 |               +-- arbiter --> address remap --> HP0 --+--->| DDR          |
 | core 1 --cut--+        |                              |    | (cores use   |
 |   |      |             +-------> mailbox BRAM <-------+----| 0x4000_0000+)|
 |   +--cc_bus (coherence)          (8 KB, shared)       |    |              |
 |                                  run bit (GPIO) <-----+----| JTAG/debug   |
 +-------------------------------------------------------+    +--------------+
```

**Core view of the address map**

| Core address | What | Notes |
|---|---|---|
| `0x8000_0000 – 0xBFFF_FFFF` | DDR, cacheable | remapped to PS DDR `0x4000_0000` |
| `0xC000_0000` | mailbox, uncached | programs write their result (`tohost`) and benchmark numbers here |

The PS sees the mailbox at `0xA000_0000` and the run bit at `0xA001_0000`.

**Why a mailbox:** the caches are write-back, so a value a core stores in DDR may stay in its cache. The PC could not see it. The mailbox is uncached, so writes go straight out.

| Item | Value |
|---|---|
| Clock | 50 MHz (timing met with 2.4 ns to spare; about 57 MHz would be possible) |
| LUTs | 58,853 of 117,120 (50%) |
| Registers | 32,058 of 234,240 (14%) |
| Block RAM | 74 of 144 (51%) |
| DSPs | 8 |
| Per core | about 25K LUTs and 41 block RAMs |

The design is not near capacity, but it has no room for two more cores at this cache size (block RAM would run out).

## How a program runs (no operating system)
Everything runs from the Windows PC over the board's USB (JTAG), using AMD's `xsdb` tool that comes with Vivado:
1. Program the FPGA with the bitstream and initialise the ARM side.
2. Hold the cores in reset and copy the program into DDR.
3. Set the run bit; both cores start at `0x8000_0000` (each reads its hart ID).
4. Poll the mailbox until the program writes its result (1 = pass), then read the benchmark numbers.

**Scripts** (in `corev_apu/fpga/kr260/`):

| Script | What it does |
|---|---|
| `kr260_build.sh [synth\|impl]` | builds the bitstream with Vivado 2023.2 on Windows, from WSL |
| `kr260_run.sh <program.elf> [timeout] [seed]` | runs a program on the board |
| `sw/link_kr260.ld` | linker script for programs (puts `tohost` in the mailbox) |
| `sim/` | a simulation stand-in for the board, used to test the exact FPGA design before building |

**Problems found on the way**
- **Two combinational loops.** Vivado's design checks found them, and they were fixed in the RTL:
  1. between the two cores' memory ports
  2. between trap handling and the cwrite check
- **Small tool issues:** the clock frequency mismatch in the block design, and `xsdb` needing the PL address range declared with `memmap`.

## Results on the board
**Correctness**

| Test | Board | Simulation |
|---|---|---|
| Coherence test (`msi_2core`) | pass, 10/10 runs | pass |
| CA test (`ca_2core`) | pass, 10/10 runs | pass |
| Same with plain loads instead of `cread` | fails, as intended (reads a freed node) | same |
| Same with a plain store instead of `cwrite` | fails, as intended (two threads in the lock) | same |
| RISC-V ISA tests | 72/73 (only `breakpoint`, disabled upstream) | 72/73 |

**No difference between the board and simulation was found.**

**Benchmarks, after the paper**
- **Setup:**
  - data structures: lazy list, external BST, Treiber stack, hash table
  - schemes: leaky `none`, `ca`, hazard pointers `hp`, epoch-based `qsbr`
  - workload: 0/10/100% updates, 1 and 2 threads, 3K operations per thread, 3 seeds
  - 288 runs, all valid (each data structure is checked after the run)

Throughput relative to `none`, 2 threads:

| | read-only | 100% updates |
|---|---|---|
| list: ca / hp / qsbr | 0.34 / 0.25 / 1.00 | 0.43 / 0.33 / 1.00 |
| BST: ca / hp / qsbr | 0.64 / 0.56 / 1.00 | 0.78 / 0.65 / 0.90 |
| stack: ca / hp / qsbr | 0.37 / 0.50 / 0.92 | **1.33** / 1.09 / 1.05 |
| hash: ca / hp / qsbr | 0.49 / 0.48 / 0.99 | **0.98** / 0.85 / 0.99 |

Nodes removed but not yet freed at the end (2 threads, 100% updates):

| | ca | hp | qsbr | none |
|---|---|---|---|---|
| nodes | **0** | about 20–35 | about 100–200 | about 1,500–3,000 |

**What matches the paper**
1. CA is slower than epoch schemes for read-only work.
2. CA is best under high contention (the stack).
3. Hazard pointers are generally the slowest.
4. CA frees memory immediately.

**Why CA reads cost more here than in the paper**
- Measured on the board: a `cread` costs 2 cycles (a plain load costs 1). The failure check (a CSR read right after it) brings the pair to 7 cycles, because CVA6 executes CSR reads only when they commit.
- The paper assumes a free flag register.
- A branch-on-failure instruction would remove most of this cost. That is a good next step.

**Caveats**
- 2 cores on a one-transaction-at-a-time bus (the paper used up to 32 simulated cores)
- 16-byte cache lines, no L2, 50 MHz
- The ratios are what to compare, not the absolute numbers.
